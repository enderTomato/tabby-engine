# ADR-008 · 3D 优化路线（分辨率、阴影、LOD、上下文丢失）

- **状态**：Accepted
- **日期**：2026-11-14
- **影响范围**：`packages/render3d`（`drs.ts` / `shadow-budget.ts` / `lod.ts` / `building-lod.ts` / `context-guard.ts` / `view3d.ts`）、`packages/assets`
- **相关**：ADR-001（混合渲染）、ADR-004（视图抽象）

## 背景

Android 优先意味着要在**同一份代码**上覆盖从骁龙 4 系到 8 系的设备。碎片化不是「三种机型」，
是同一颗 GPU 在不同驱动、不同热状态下表现都不同。所以优化不能靠「把参数调低」，要靠
**运行时可测、可退的机制**。

需求里列了五项：KTX2 纹理、建筑 LOD、CSM 阴影、动态分辨率（DRS）、上下文丢失恢复。
五项的成本收益差得很远，不适合当成一组一起做。

## 可选方案

| 子项 | 做法 | 移动端收益 | 成本 | 风险 |
|---|---|---|---|---|
| 上下文丢失恢复 | 监听 `webglcontextlost` + `preventDefault` + 恢复后重建 | **极高**（不做就是白屏且永不恢复） | 低 | 低 |
| 动态分辨率 | 帧时间中位数驱动，乘在 `renderScale` 上 | **高**（填充率是主因） | 低 | 抖屏（需迟滞/冷却） |
| 建筑 LOD | 近处实例化方盒 / 远处 billboard | 中高（远景 DrawCall 与三角形同时降） | 中 | 分界线闪烁；无贴图时必须降级成剪影 |
| KTX2 纹理 | 压缩纹理 + 解码器按需拉取 | 中（显存与带宽） | 中 | 解码器 900KB 不能进主包 |
| CSM 级联阴影 | 4 级级联 shadow map | **负**（4 次 shadow pass） | 高 | 移动端纯亏 |

## 决策

### 1. 做：上下文丢失恢复

这是**稳定性缺陷**而不是优化项。漏做的表现是用户切后台回来看到一片黑，且永远不会恢复
（浏览器默认不去救没有 `preventDefault()` 的丢失事件）。恢复要延迟一帧再重建 GPU 资源，
否则有概率拿到 `INVALID_OPERATION`。

### 2. 做：动态分辨率，参数带三重防抖

目标帧时间跟档位走（低端 33.3ms / 60fps 档 16.7ms）。用**中位数**而不是平均值（一次 GC
能把平均拉爆）；降档阈值 1.15×、升档 0.85×（迟滞区 30%）；两次调整至少隔 1.5s
（改分辨率本身要重建 drawing buffer，立刻重评估会读到自己造成的掉帧，然后一路降到底）。

### 3. 做机制、不做资产：建筑 LOD

`classifyLod` 用迟滞（进 26m / 出 30m）避免分界线闪烁，遍历序固定（确定性红线）。
贴片几何、朝向、批量写入都真做；**贴图留接口**（`setImpostorTexture`），因为没有烘焙管线 ——
假装做过烘焙比留空更糟。无贴图时是纯色剪影，属于可用降级态。

### 4. 不做 CSM，改「阴影预算」

CSM 在 PC 上几乎免费，在手机上是纯负收益：4 级级联 = 每个投影物画 4 遍，
DrawCall 直接 ×4，而我们的可视距离被雾切在 40~80m，「近精细远覆盖」的矛盾并不尖锐。

替代：按档位给预算 —— 低端全关、中端单级 512²、高端**两盏独立平行光**（近 1024²/18m +
远 512²/60m）。两盏灯不是级联，没有拼接缝也没有动态切分。DRS 掉到 0.85 以下时阴影同步减半：
GPU 已经吃紧时，最贵的那个 pass 不该独占预算。

### 5. 做：KTX2 接入，解码器永不进主包

`basis_transcoder` 527KB + `draco_decoder` 285KB。进展主包意味着「只想画几个方块」的游戏
也要先下 1MB。所以解码器由部署方托管在 `public/decoders/`，加载器本身走动态 `import()`。
能力探测 → 候选链 → 实际加载 三步分离，回退次数（`fallbacks`）是线上最有用的一个数字。

## 后果

**好的**：

- 低端机上「能跑」的下限被抬起来了：分辨率会自动让路，阴影直接关掉，远景降成贴片。
- 上下文丢失有明确的恢复路径，不再是「偶发白屏，重启解决」。
- 所有决策都能在 demo 的诊断面板与 playground 的探针里被看见和测量。

**代价**：

- 多出四个小模块与一组状态（DRS 状态机、阴影计划、LOD 分类、guard），`view3d` 从 360 行涨到 600 行。
- LOD 在没有烘焙贴图前，远景建筑是纯色片 —— 观感上比「全是方盒」单调。
- 阴影「两级靠两盏灯」比 CSM 粗糙：中远景的阴影分辨率是固定的，不像级联那样随距离自适应。

**后续**：

- 有资产管线之后，`setImpostorTexture` 接上 8 方位图集，并按方位挑 UV（需要在实例属性里加 uvOffset）。
- 若将来要做大地图（可视距离 > 150m），阴影预算可能要重新评估，或引入「只在近处投影」的剔除。
- DRS 目前只按帧时间调，未来可以叠加「GPU timer query」做更前置的判断，但那是浏览器扩展，覆盖率优先。
