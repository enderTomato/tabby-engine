# ADR-007 · 格子归属的唯一真相

- **状态**：Accepted
- **日期**：2026-11-14
- **影响范围**：`apps/demo/src/game/*`、`packages/economy`
- **相关**：ADR-005（包拆分）、T15（经济内核）

## 背景

`@tabby/economy` 是独立包，自带实体池（`alive` / `buildingTile` / `buildingType`）。
demo 的 `city.ts` 在接入经济内核之前也有一份 `cells: CellKind[]`，以及配套的
`coins` / `houses` / `farms` / `farmWater`。两套数据结构描述的是同一件事：
**哪个格子有什么建筑**。

合并时会立刻遇到一个必须显式回答的问题：**谁是真相**。

不回答的话，默认结果一定是"两个都是"——放置时写一边、结算时读另一边，然后出现
"看得见建筑但拆不掉"、"拆了还在产粮"这类只在特定操作序列下复现的 bug。

## 可选方案

| 方案 | 做法 | 成本 | 后果 |
|---|---|---|---|
| A. 经济层接管 | `city.ts` 降级为几何/样式模块，格子归属只查经济层实体池 | 中：渲染与 UI 全部改读经济层，需加一层投影缓存 | 单一真相；排查任何"对不上"只需看一处 |
| B. 双写 + 同步层 | 保留两份，用一个 sync 函数双向对齐 | 低：改动最小 | 必然存在不一致窗口；sync 本身的正确性无法被验证（它自己就是真相裁判） |
| C. 各管各的 | demo 只跑经济模拟，不做格子联动 | 最低 | 验证不了指令队列、验证不了"建造 → 聚合 → 税收"整条链路 |

## 决策

**选 A。**

具体拆成两层：

```
Economy.state（TypedArray 实体池）  ← 唯一真相
        │  building-placed / building-removed 事件（增量）
        ▼
CitySimulation.cells / entityAt     ← 投影缓存（Int8Array / Int32Array）
        │
        ├→ obstaclesOf() / zonesOf()  → 物理引擎的碰撞盒与吸收区
        └→ obstaclesOf() → 2D/3D 渲染几何
```

`city.ts` 不再持有任何游戏状态，只剩网格坐标换算、配色表、以及"格子快照 → 物理几何"的
纯函数。它连 `@tabby/economy` 都不 import —— 几何层不需要知道建筑有维护费。

### 投影为什么是缓存而不是每次现算

经济层的映射方向是 `实体 id → tile`（`buildingTile[id]`）。渲染需要的是
`tile → 类型`。每次渲染遍历 4096 个槽位反查，在 60Hz 下是纯浪费；而且建造/拆除是
低频操作（人手点击），完全负担得起"变更时增量维护、读档时全量重建"。

### 怎么保证缓存不漂

三条防线，按发现成本从低到高：

1. **写路径唯一**：所有变更走 `economy.applyCommand`，投影只由事件回调更新。
   没有 `setCellDirect` 之类的后门。
2. **`rebuild()` 全量重建**：读档、`init` 这类批量替换后强制调用，
   因为批量变更不会逐个发事件。
3. **`verifyProjection()` 一致性自检**：拿实体池反查投影，逐格比对，
   诊断面板实时显示 `投影自检 ✓ 投影一致（72 格）`。
   一旦有人绕过指令队列直接改 `state`，这里立刻变红 —— 这是整套设计的保险丝。

自检也进了测试：每个用例结束都断言 `verifyProjection().ok`，
包括建造、拆除、拆越界、金币不足、跑 3 年、存档往返。

## 接入过程中修掉的缺陷

合并两套数据的过程本身就是一次代码审查。以下四个问题在"只跑单元测试"时都不会暴露：

### 1. `building-removed` 事件的 payload 全是错的

```ts
this.state.destroy(id);
this.bus.emit('building-removed', { id, city, def: this.state.buildingType[id] });
//                                                    ^^^ destroy 已把它归零
```

`destroy` 会把 `buildingType` 置 0、`buildingTile` 置 -1。事件在 `destroy` **之后**读这两个字段，
于是所有拆除事件都报 `def = 0`（住宅），`tile` 拿不到。
订阅方按 `def` 更新投影时，会把农田拆成住宅。

修法：在 `destroy` 前抓下 `defIndex` / `tile`，并在事件类型里补上 `tile` 字段。

### 2. 人口取整把小城市彻底锁死

`runPopulation` 原本是 `Math.round(pop + delta)`。drift 是 `(满意度 - 0.5) × 0.08`，
8 人村庄满意度 0.95 时 delta = 8 × 0.45 × 0.08 = **0.288**，`round(8.288)` 还是 8。
每天白算一次，人口永远长不大；反过来断粮也不掉人。

锁死阈值约在 15 人（`1 / (0.045 × 0.08)`），也就是"新手村永远停在 8 人"这种
最难被察觉的形态 —— 大人口测试里永远测不出来。

修法：内核允许小数，只在展示层 `Math.round`。Float32 的加减乘是 IEEE754 精确定义的，
跨设备逐位一致，不会破坏确定性。

### 3. 物理几何与渲染几何的 z 坐标错位

`obstaclesOf` / `zonesOf` 里 z 写死 `±1.6`，而 3D 渲染按 `row` 算 z。
结果"看得见的建筑"和"能撞到的建筑"是两套位置：布娃娃穿过楼、水从墙边漏过去，
而且从 2D 视图完全看不出来。

同时 `ROW_TO_Z = -4` 让最后一行伸出物理世界边界（±6），碰撞盒有半截在界外。

修法：抽出 `zSpanOf(row)`，物理几何与渲染共用同一个函数；`ROW_TO_Z` 改成 -6，
6 行 × 2 正好铺满 12 深度。

### 4. 默认建筑表在 demo 里会让人饿死

`DEFAULT_BUILDINGS` 的农田有 `input: [[Power, 0.4]]`，而 demo 没有发电站 ——
电力库存恒为 0，`runProduction` 按 `have / amount` 缩产到 0，于是"田建好了人照样饿死"。

修法：demo 自建一张 3 项的小表（住宅/农田/挡板），农田无输入，挡板有 0.5 的维护费
（否则最优解是铺满挡板，玩法塌掉）。表顺序与默认表前两项对齐，追加的挡板放末尾。

## 后果

**收益**

- 建筑、人口、价格、税收、存档全部来自同一个实体池，不存在"两边数字不一样"的情况
- demo 验证了完整的指令队列链路：点击 → `applyCommand` → 事件 → 投影 → 物理几何 → 渲染
- 经济内核的 `save()` / `load()` 第一次被真实消费，暴露了上面第 1 条 bug

**代价**

- 渲染读格子多了一层间接（`sim.cellAt(col,row)` 而不是 `city.cells[i]`），
  成本可忽略，但任何新增的格子属性都要想清楚"它是投影还是真相"
- 投影缓存本身是第二份数据，必须靠自检兜底。这是**刻意保留的复杂度**：
  换成每次现算就没有这个风险，但会牺牲 60Hz 下的确定性开销
- demo 的建筑表与经济层默认表分叉，两份表都要维护

**已知未解决**

- 食物没有消费出口，库存单调上涨，粮价必然钉在 `0.3 × 基准` 下限。
  这是模型缺失（没有贸易/腐烂），不是参数问题 —— 调 `targetStock` 只能改变钉死的时间点。
  demo 因此在 HUD 上显示"产/耗"而不是粮价，诊断面板里才给价格并标注"已触下限"
- `runLogistics` 仍是空实现，`buildingEfficiency` 只受维护费影响
- 经济层没有分帧摊销：4096 容量下 1.4ms/日不是问题，但 50k 实体 + 60Hz 会撞穿 CPU 预算
